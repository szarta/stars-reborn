Binary ``.xN`` Order File Format
================================

|original| stores per-player turn orders in files named ``Game.xN``,
where *N* is the 1-based player number (``Game.x1`` for player 1, up to
``Game.x16``).  Each file holds an ordered sequence of *order records*
generated by the player's client during the turn-edit phase and read
back by the host at turn resolution.

The reference parser is :file:`stars_file_parser/src/bin/x1_to_json.rs`;
this document captures the same byte-level knowledge in a form
accessible to engine and client implementers.

File Container
--------------

``.xN`` files share the same container layout as ``.m`` and ``.hst``
files:

.. list-table::
   :header-rows: 1
   :widths: 12 15 15 58

   * - Section
     - Type
     - Length
     - Notes
   * - File header
     - 8 (plaintext)
     - 16 B
     - Bytes 0–11 carry the game/turn identity (must match the current
       ``.m`` for that player).  Bytes 12–15 seed the L'Ecuyer LCG that
       encrypts the rest of the file.  Stars rejects mismatches
       silently.
   * - File info
     - 9 (encrypted)
     - 17 B
     - 2-byte LE ``LengthOfFollowingBlocks`` + 15-byte machine hash.
   * - Order records
     - 1–63 (encrypted)
     - varies
     - One record per order action, in submission order.
   * - End marker
     - 0 (plaintext)
     - 2 B
     - Empty record signalling end of file.

Each record begins with a 2-byte little-endian header word:

.. code-block:: text

   bits 15..10 = record type (0–63)
   bits  9..0  = payload length in bytes (0–1023)

Payload bytes are XOR-encrypted with the L'Ecuyer keystream seeded by
the file header.  See :file:`stars_file_parser/src/cipher.rs` for the
full algorithm.

Player Identity
~~~~~~~~~~~~~~~

The 0-based player index is encoded in the low 5 bits of the seed word
at offset 12–13 of the type-8 header.  ``x1_to_json`` exposes this as
``player_idx`` in its output.

Confirmed Record Layouts
------------------------

Common encodings used throughout:

- **9-bit fleet number** (``fleet_num``): byte 0 is the low 8 bits;
  bit 0 of byte 1 is the high bit.  Range 0–511.  Bytes 0–1 are read
  as a little-endian uint16 with only the low 9 bits significant.
- **LE uint16**: standard little-endian unsigned 16-bit integer.
- **Stars name**: 1-byte length prefix followed by nibble-packed bytes
  using the original Stars text codec (see :file:`name.rs`).

Type 1 — Manual Cargo Transfer
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Immediate cargo transfer at the fleet's current planet (waypoint-0).
Variable length depending on how many resource types are involved.

.. code-block:: text

   b0–b1   fleet_num    (9-bit)
   b2–b3   planet_idx   (LE uint16)
   b4      action_byte  (0x12 = load, 0x02 = unload)
   b5      resource_mask (bit 0 iron, 1 boran, 2 germ, 3 colonists)
   b6+     amounts      (one byte per set bit, ascending bit order; kT)

Confirmed via R0.7 oracle (2026-04-20/21).

Type 3 — Waypoint Delete
~~~~~~~~~~~~~~~~~~~~~~~~

.. code-block:: text

   b0–b1   fleet_num    (9-bit)
   b2      waypoint_nr  (0-based index into route)

Type 4 / Type 5 — Waypoint Add / Change Task
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Identical 12-byte (+ optional transport) layouts.  Type-4 establishes a
new waypoint; type-5 sets/changes its task and is **authoritative for
the task** when both are present.

.. code-block:: text

   b0–b1   fleet_num    (9-bit)
   b2      waypoint_nr
   b3      reserved (always 0)
   b4–b5   dest_x       (LE uint16)
   b6–b7   dest_y       (LE uint16)
   b8–b9   target       (LE uint16; planet or fleet index — full 16 bits)
   b10     warp_speed << 4 | task_type
   b11     target_type  (low nibble)
   b12+    transport payload (only when task_type == 1)

``task_type`` codes:

.. list-table::
   :header-rows: 1
   :widths: 8 22 70

   * - Code
     - Task
     - Notes
   * - 0
     - None
     - Movement only.
   * - 1
     - Transport
     - Followed by 10 transport-payload bytes.
   * - 2
     - Colonize
     - Requires colonists in cargo.
   * - 3
     - Remote Mining
     - Ships with Remote Mining equipment.
   * - 4
     - Merge with fleet
     - ``target`` is the destination fleet number.
   * - 5
     - Scrap fleet
     - At the destination's starbase.
   * - 6
     - Lay mine field
     - Requires mine layers.
   * - 7
     - Patrol
     -
   * - 8
     - Route
     - Forwards arrivals to the planet's set route target.
   * - 9
     - Transfer fleet
     - ``target_type`` field encodes the receiving player.

**Transport payload (type-1 task only)**: 10 bytes, two per resource in
the fixed order ironium, boranium, germanium, colonists, fuel.  Each
pair is ``(amount_lo, (action << 4) | (amount_hi & 0xF))``:

.. list-table::
   :header-rows: 1
   :widths: 14 22 64

   * - Action
     - Name
     - Notes
   * - 0
     - None
     - Pair is (0, 0) — trailing zeros may be omitted.
   * - 1
     - Load all available
     -
   * - 2
     - Unload all
     -
   * - 3
     - Load exact amount
     - ``amount`` in kT (fuel: percent 0–100).
   * - 4
     - Unload exact amount
     -
   * - 5
     - Fill up to amount
     -

Confirmed via x1 oracle 2026-04-17 for actions 1/2/3/5; 4 inferred.

Type 10 — Waypoint Repeat Orders
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

.. code-block:: text

   b0–b1   fleet_num    (9-bit)
   b2–b3   repeat_flag  (LE uint16; 1 = on, 0 = off)

Type 23 / Type 24 — Move Ships / Fleet Split
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Always emitted as a pair.  Type-23 carries the selection mask; type-24
identifies the source fleet.

**Type 23**:

.. code-block:: text

   b0–b1   src_fleet     (9-bit)
   b2–b4   unknown (constant within a fleet config)
   b5      design_mask   (bit k = move ALL ships of design slot k)
   b6      unknown
   b7–b8   dst_fleet     (LE uint16; 0xFFFF = create new fleet)

**Type 24**:

.. code-block:: text

   b0–b1   fleet_num    (9-bit)

``design_mask`` bits 2 (Santa Maria) and 3 (Teamster) are confirmed;
other bits and the unknown bytes have not been decoded but are
constant for a given fleet configuration.

Type 27 — Ship/Starbase Design Delete / Save
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Two forms distinguished by length.

**Short form (2 B) — delete design:**

.. code-block:: text

   b0   subtype       (0x00 = delete-by-slot)
   b1   design_slot   (0-based index into the player's design list)

Confirmed via shoestring-wm GUI oracle (2026-07-13): from the Ship & Starbase
Designer, *Delete Selected Design* on slots 0/1/2 emitted payloads
``00 00`` / ``00 01`` / ``00 02`` respectively (slot 0 = the starting *Armed
Probe*).  The research corpus also carries short records with a nonzero first
byte (``80 01``, ``b0 01``) — a not-yet-identified subtype (edit/create
reference?), distinct from the plain delete above.

**Long form (34–80 B) — design create/save:**

Emitted by *Copy Selected Design* → edit → *OK* in the designer.  Partially
decoded (oracle 2026-07-13); full slot-tuple layout pending dedicated
component-varying runs.  A captured 44-byte *Armed Probe* copy:

.. code-block:: text

   01 e6 07 19 04 11 14 00 03 00 00 00 00 00 00 00 00 00 00 01
   00 03 01 02 00 01 01 10 00 01 01 0d b0 8d b2 d6 0b f8 7d 42
   0f 82 cc f9 2f

Byte 2 (``0x07``) and byte 6 (``0x14``) are **invariant** across captured
samples and the research corpus long sample
(``21 b2 07 48 22 89 14 05 0c …``), anchoring the format.  The tail
(``… 0d b0 8d …``) is the Stars-name-encoded design name (``0d`` length
prefix).  The reference parser surfaces this form as ``design_save`` with the
raw payload until the slot tuples are decoded.

Type 29 — Production Queue Replace
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Replaces the *entire* production queue at one planet.

.. code-block:: text

   b0–b1   planet_idx   (LE uint16; low 11 bits)
   b2+     items[]      (4 bytes per entry)

Each entry is two LE uint16 words:

.. code-block:: text

   word0 = (item_id << 10) | count
   word1 = (complete_percent << 4) | item_type

``item_type`` codes:

.. list-table::
   :header-rows: 1
   :widths: 10 25 65

   * - Code
     - Type
     - ``item_id`` interpretation
   * - 2
     - Standard item
     - 7=Factory, 8=Mine, 9=Defenses (others TBD).
   * - 4
     - Custom design
     - 0-based design slot index.

Type 30 — Battle Plan Upsert
~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Creates or updates a battle plan; built-in slots 0–4 are
Default/KillSB/MaxDef/Sniper/Chicken, 5+ are user-defined.

.. code-block:: text

   b0      plan_index << 4   (low nibble unused)
   b1      tactic
   b2      (secondary << 4) | primary    (target priorities)
   b3      attack_who
   b4+     name (Stars name encoding)

``tactic`` codes: 0=Disengage, 1=DisengageIfChallenged, 3=MaxNetDamage,
4=MaxDamageRatio.  ``primary``/``secondary``: 0=None, 1=Any, 2=Starbase,
3=Armed, 4=Bombers, 5=Unarmed, 6=FuelTransports, 7=Freighters.

Type 34 — Research Change
~~~~~~~~~~~~~~~~~~~~~~~~~

.. code-block:: text

   b0   research_percent (0–100, percent of resources allocated)
   b1   (next_field << 4) | current_field

Field codes: 0=Energy, 1=Weapons, 2=Propulsion, 3=Construction,
4=Electronics, 5=Biology, 6=SameField (continue current after current
completes).

Type 37 — Fleets Merge
~~~~~~~~~~~~~~~~~~~~~~

Merges one or more source fleets into the destination ``fleet_num``.

.. code-block:: text

   b0–b1   fleet_num         (9-bit; merge destination)
   b2+     merge_targets[]   (one LE uint16 per source; low 9 bits)

Type 42 — Set Fleet Battle Plan
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

.. code-block:: text

   b0–b1   fleet_num    (9-bit)
   b2–b3   plan_index   (LE uint16; 0–4 built-in, 5+ custom)

Type 44 — Rename Fleet
~~~~~~~~~~~~~~~~~~~~~~

.. code-block:: text

   b0–b1   fleet_num    (9-bit)
   b2–b3   reserved (always 0)
   b4+     name (Stars name encoding)

Unknown / Open Record Types
---------------------------

Three opcodes are observed in the research corpus but not yet decoded.
Each is the subject of a separate oracle task in the work queue.

Type 2 (8 B) — *fleet-create / new-fleet metadata*
   Always paired with a following ``waypoint_add`` for the same fleet.
   Sample payloads:

   .. code-block:: text

      a4 01 35 0c 21 08 fa 00     (fleet 420 follows; waypoint added)
      44 0c fc 01 12 08 fa 00
      f7 01 18 16 21 08 fa 00

   Bytes 6–7 are consistently ``fa 00``; bytes 4–5 are ``12 08`` or
   ``21 08`` (look like flag fields).  Hypothesis: this is the order
   that *creates* a new fleet from a fleet-split or scoop-from-cargo
   action and assigns its initial id.

Type 35 (6 B) — *planet packet target / planet flag*
   Bytes 0–1 are a ``planet_idx`` that matches the planet of the next
   ``production_queue_change`` record in file order.  Bytes 2–5 vary:
   AI samples carry ``01 00 00 00``; human samples carry larger values
   (e.g. ``26 25 00 00``).  Hypothesis: mineral-packet destination set
   by the player on a planet with a mass driver.

Suspected Missing Record Types
------------------------------

The following player actions are part of |original|'s rules but produce
no records in our current corpus, either because the games we sampled
did not use the feature, or because we have not yet identified the
opcode:

- Mineral packet launch (manual one-shot from a mass driver)
- Stargate / wormhole gating order (likely encoded as a waypoint task)
- Planet rename
- Planet route-to target (separate from the per-fleet route waypoint
  task)
- Auto-build / starbase-mass-driver target setting
- Player-relations changes (set friend/enemy/neutral)
- Game messages (chat / send-to-player)
- Designate research-only colony / "contribute leftover energy" toggle

Oracle work to confirm each is tracked as separate research tasks.

Determinism and Idempotency
---------------------------

|original| applies orders in file order during turn resolution.  Most
order records are *idempotent replacements* of game state (e.g.
``production_queue_change`` replaces the entire queue rather than
patching it), which makes the file safe to truncate and rebuild on
every save during the edit phase — the behaviour the original UI
implements.

Two record types — type-1 ``manual_cargo_transfer`` and the
type-23/24 fleet-split pair — are *event-style* and are applied
incrementally; the engine must therefore preserve order and not
deduplicate them.

Implementation Notes
--------------------

Stars Reborn does **not** consume ``.xN`` files at runtime.  The legacy
parser converts each record into the engine's native JSON order
representation (see :doc:`engine_api`) at import time, and the engine
operates only on JSON thereafter.  This keeps the rules layer free of
binary-format details and lets future order types be added without
touching the parser.
